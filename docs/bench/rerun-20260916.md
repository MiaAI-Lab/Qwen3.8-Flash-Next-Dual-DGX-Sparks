# Three-arm decode re-run — 2026-09-16

An independent re-measurement of the reduced-vocabulary MTP drafting default,
run fresh in a single session alongside the configuration it replaced and the
configuration that preceded both.

## Setup

One launch per arm, everything else identical: nvidia NVFP4, TP2+EP, MTP 3,
BF16 SSM, 262,144 context, `MAX_NUM_SEQS=8`, NFS-shared weights, stock QSA.
`bench/sweep.py` driving sparkDash, 600 tokens, S=1/2/4/8, prose and code,
3 repeats each in alternating stream order. 24/24 rows per arm, zero
`NV_ERR_NO_MEMORY` events.

| arm | KV dtype | draft head | KV pool | concurrency @262k |
|---|---|---|---|---|
| `orig` | bf16 (`auto`) | full 248,320 | 2,426,193 tok | 9.26× |
| `fp8kv` | fp8 | full 248,320 | 4,378,829 tok | 16.70× |
| `tuned` | fp8 | 47,149 | 4,378,829 tok | 16.70× |

## Result: reduced-vocabulary drafting

`fp8kv` → `tuned`, the change this document exists to measure:

| workload | change |
|---|---|
| **all (n=8)** | **+8.4%** |
| prose (n=4) | +7.4% |
| code (n=4) | +9.3% |

The gain is entirely step time, with acceptance unchanged:

| cell | ms/step | tok/step |
|---|---|---|
| prose S=1 | 59.3 → **51.9** | 3.00 → 2.92 |
| code S=1 | 60.7 → **54.0** | 3.82 → 3.83 |

This is the mechanism the patch was built for: the drafter's own
248,320-row BF16 `lm_head` is read once per draft step — three of the four
`lm_head` reads in an MTP=3 engine step — and slicing it to a frequency-ranked
subset cuts the bytes without moving acceptance. Output is unaffected by
construction: drafts are verified against the target model, so an id outside
the subset is rejected exactly like any other bad draft.

### Relationship to the 2026-09-11 A/B

Same direction and magnitude class (+9.6% then, +8.4% here), but **not a
cell-by-cell reproduction**. Per-cell deltas move −5.0 to +3.6 points
(prose S=2 +8.9% → +3.8%; code S=8 +4.0% → +7.7%) while within-session
3-repeat stdev is only 2.0–5.0% of the mean. The means agreeing is partly
cancellation. Treat the mean as the reproducible quantity, not the cells.

## Secondary finding: fp8 KV is a capacity/throughput trade

Recorded here because the same experiment measured it; tracked separately, as
it concerns a default shipped before this change.

fp8 KV costs **−5.3%** mean throughput (−1.4% prose, −9.2% code), the cost
growing with concurrency. Two mechanisms, separable in the data:

- `tok/step` falls in **8 of 8 cells** — the QSA sparse-indexer perturbation
  already noted in `CHANGELOG.md`: quantised keys change *which blocks the
  indexer selects*, so the drafter sees different context and acceptance drops.
- `ms/step` is flat at S=1 (60.5 → 60.7) but +11% at S=8 (84.9 → 94.6): more
  sequences, more KV reads, more scale-application work.

What it buys is capacity: **1.80×** the cache (2,426,193 → 4,378,829 tokens),
9.26× → 16.70× concurrency at 262k. That is what makes long-context
multi-stream serving viable on this kit, and is a good reason to keep it — but
it is a trade, not a free win, and the CHANGELOG presents only the capacity
side.

## Caveats

1. **The `code` prompt is synthetic.** sparkDash's code workload is 50
   byte-identical `clamp_NN` helpers differing only by a two-digit suffix; its
   own source describes it as *"High-accept code: repeated identical-shape
   helpers."* Arm 1 measures `p1/p2/p3 = 1.00/0.99/0.99`, i.e. the drafter at
   saturation. Valid for A/B deltas — both arms run the same prompt — but not
   representative as an absolute, and it leaves no acceptance headroom. `prose`
   (`0.81/0.64/0.51`) is the representative column. This applies equally to the
   2026-09-11 table in `CHANGELOG.md`, which does not state it.

2. **Arm 3 carries a session-condition asterisk.** `orig` and `fp8kv` ran under
   one driver with a clean sequential teardown. That driver was then killed by
   host memory pressure; `tuned` swept against the container its launch had
   already started, while the host was at 85 GiB used with 8 GiB swapped. Rows
   are clean (24/24, `nvrm=0`, `ms/step` moving as predicted) and are kept, but
   the fp8-vs-bf16 comparison is the better-controlled one.

   The pressure was NFS weight streaming filling the page cache — a live
   reproduction of issue #35 on the vLLM path.

3. **Nothing reaches past `orig`.** The SGLang → vLLM replacement (`6e08722`)
   and the checkpoint swap to nvidia NVFP4 are not behind env knobs, so no
   cumulative figure here extends to them. They are not folded into any
   headline.
